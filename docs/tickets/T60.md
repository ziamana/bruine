# T60 — Keys are keys, not bytes

## The problem
`QuestionForm.handleInput` compared raw bytes: `data === "\x1b[A"`, `"\r"`,
`"\x7f"`, `" "`. pi-tui turns the kitty keyboard protocol on when the terminal
advertises it, and that changes the bytes: an arrow arrives as `CSI 1;1 A`, a
typed letter as `CSI 97 u`, and **a release event after every press**. So the
form was correct only on a terminal without the protocol, and on the others
Up/Down did nothing at all.

The audit found the same class in three more places, and one of them is worse:

| place | what broke under kitty |
|---|---|
| `ui/questions.ts` | arrows, space, enter, escape, typing: the form was frozen |
| `setup/full.ts` (text field) | **typing did nothing**: the `startsWith("\x1b")` guard dropped every `CSI 115 u` |
| `setup/full.ts` (item picker) | space and enter, and the `s` skip shortcut |
| `ui/kumo-ui.ts` (ghost suggestion) | right and ctrl+f did not accept the ghost; Enter did not suppress it; typing did not clear it, so a background suggestion was never dismissed |

## What it does
Every key goes through `matchesKey`, which reads both encodings, and every
key-release is dropped first: with the protocol on, a press *and* a release
arrive, and `matchesKey` answers yes to both, so without that filter one
backspace erases two characters and one arrow walks two rows.

Printable text is the one thing `matchesKey` does not answer, so it is read in
one place (`ui/keys.ts`), for both encodings, and nowhere else.

## The guard
A bug that was a comparison gets a test that is a comparison: `test/keys.test.ts`
scans `src/{ui,setup,plugins}` and fails on any `data === "\x1b…"`,
`data === "\r"`, `data.startsWith("\x1b")`. Verified by reintroducing the exact
comparison that broke: the test names the file and the line.

The encodings in the tests are the ones pi-tui itself accepts, probed against
`matchesKey` rather than taken from the specification.

## Out of scope, on purpose
- `shift+arrow` and `ctrl+backspace`, which pi-tui's matcher does not answer to
  either. They did nothing before and do nothing now; the form never promised them.
- Key rebinding per component. `matchesKey` takes a key id, so a future
  `keybindings` entry is a one-line change, and until then the ids are the
  defaults pi-tui already documents.
- The editor itself: pi-tui's `Editor` decodes the protocol, which is why typing
  in the prompt always worked and only the custom components were broken.

## Checks
`pnpm typecheck`, `pnpm test`, `pnpm test:e2e`.

## Files
`src/ui/keys.ts` (new), `src/ui/questions.ts`, `src/setup/full.ts`,

## Acceptance
- The form walks options, questions, toggles and answers, in both encodings.
- A key release moves nothing and erases nothing.
- The wizard's text field accepts a typed letter in both encodings.
- The ghost suggestion is accepted with right and ctrl+f, and cleared by typing,
  in both encodings.
- No file under `src/{ui,setup,plugins}` compares a key by its bytes.
