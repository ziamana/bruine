# T62: herdr integration: kumo reports its state

In a [herdr](https://herdr.dev) pane, `herdr agent list` shows OpenCode as `working` / `idle` / `blocked`, but kumo as
`unknown`: herdr only knows agents that report themselves. With this ticket, kumo reports its own state, so herdr's
agent list, `herdr agent wait` and notifications work with kumo like with OpenCode or Claude Code.

## Mechanism (proven 2026-09-27 against herdr 0.9.1)

herdr sets three variables in every pane it manages. kumo does nothing unless all three are present.

| Variable | Value |
|---|---|
| `HERDR_ENV` | `1` |
| `HERDR_SOCKET_PATH` | Unix socket path. On Windows the endpoint is `\\.\pipe\<HERDR_SOCKET_PATH>` (same rule as herdr's own OpenCode plugin) |
| `HERDR_PANE_ID` | e.g. `wG:p2` |

One request = one connection, one JSON line, one JSON line back (`{"id":…,"result":{"type":"ok"}}`), then close.

```json
{"id":"kumo:<ms>:<rand>","method":"pane.report_agent","params":{"pane_id":"wG:p2","source":"kumo","agent":"kumo","seq":1790550000000001,"state":"working","agent_session_id":"<dsh session id>"}}
```

- `state`: `idle` | `working` | `blocked` (herdr also has `unknown`, never sent).
- `seq`: strictly increasing within the process. Start at `Date.now() * 1000`, then +1 per request.
- `pane.report_agent_session` `{pane_id, source, agent, seq, agent_session_id, session_start_source: "new"}` on `/new`.
- `pane.release_agent` `{pane_id, source, agent, seq}` on exit, so the pane stops showing kumo.

Verified by hand: after a `pane.report_agent` with `agent: "kumo"`, `herdr agent list` printed `wG:p2 kumo idle`;
`pane.release_agent` removed it. The schema (`herdr api schema --json`, `PaneReportAgentParams`) declares `agent` and
`source` as free strings.

## State mapping (interactive REPL only, not `kumo -p`)

| kumo event | State |
|---|---|
| REPL ready (after the banner) | `idle` + `agent_session_id` |
| `session/event` `turn/start` | `working` |
| `approval/request` or `user-questions/request` waiting for the user | `blocked` |
| approval or question answered | `working` |
| `turn/end`, reason normal or aborted | `idle` |
| `turn/end`, reason error | `blocked` (needs a human, same choice as herdr's OpenCode plugin) |
| `/new` | `pane.report_agent_session` with `session_start_source: "new"`, then `idle` |
| exit (`/exit`, Ctrl+D, SIGINT, SIGTERM) | `pane.release_agent` |

## Rules

1. **Never slow or break kumo.** Fire and forget; requests are chained so they arrive in order; 500 ms timeout per
   request; every error (no socket, refused, timeout, bad reply) is swallowed silently. Nothing is printed, ever, not
   even in debug output shown to the user.
2. **Zero cost outside herdr.** If one of the three variables is missing, the plugin registers nothing and opens nothing.
3. **No dependency.** `node:net` only. No herdr package, no herdr binary call.
4. **Cross-platform.** Unix socket on Linux/macOS, named pipe on Windows (see table above).
5. Exit must not wait more than 500 ms for the release.

## Files

- `src/plugins/herdr.ts` (new): the reporter (pure `reportState` / `release` over an injectable `connect`) and the
  plugin that listens to the events above.
- `tsup.config.ts`, `cordis.patch.yml`: register `kumo-code/herdr` like the other plugins.
- `test/herdr.test.ts` (new): a fake herdr server (`net.createServer` on a temp socket, a named pipe on Windows)
  that records the lines it receives.
- `README.md`: one line under features, "Works with herdr: shows up as `kumo` in `herdr agent list`."

## Acceptance

Unit (fake server):
- Env missing (each of the 3 variables in turn) → the server receives nothing.
- A scripted turn with one approval → exactly `idle, working, blocked, working, idle`, each with `agent: "kumo"`,
  `pane_id` from the env, `seq` strictly increasing.
- Error turn → ends on `blocked`. `/new` → one `pane.report_agent_session` with `session_start_source: "new"`.
- Server down, and server that never answers → no throw, the turn is not delayed by more than 500 ms.
- Exit → `pane.release_agent` is the last line.

Manual (report the output), inside a herdr pane with `KUMO_HOME=$(mktemp -d)`:
1. Start kumo → `herdr agent list` shows `kumo idle` for that pane.
2. Send a prompt → `kumo working` during the turn, `kumo idle` after.
3. In Ask mode, trigger an approval → `kumo blocked` while the select is open.
4. From another pane: `herdr agent wait <pane_id> --state idle` returns when the turn ends (check `herdr agent wait --help` for the exact flags).
5. Quit kumo → the pane no longer shows `kumo`.
