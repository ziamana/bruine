# T22 — End-to-end tests in a REAL terminal (pty + headless xterm)

Nothing today proves the UI in a real terminal: Escape, Tab, the single reasoning line, the approval select, resize.
Aron rated the old UI 0/10 on exactly these points. This ticket builds the robot that checks them, on 3 OS.

**Work in the git worktree `../kumo-e2e` (branch `t22-e2e`). Another agent is editing `src/` in the main checkout.**

## Files (create only, except package.json / lockfile)
- `test/e2e/**` (harness, own SSE server, scenarios, `__screens__/`)
- `package.json`: devDependencies `node-pty`, `@xterm/headless` (both MIT); script `"test:e2e": "vitest run test/e2e"`
- `pnpm-lock.yaml`, `vitest.config.*` only if needed to keep e2e out of the default `pnpm test`
- **Do NOT modify `src/` nor `test/cache/`.** If a scenario fails because of a kumo bug: stop, report the bug with the
  screen dump. Finding bugs is the goal of this ticket.

## Harness
- Build first (`pnpm build`), spawn `node dist/bin.js` in node-pty, 100×30, `DSH_HOME` = `mkdtemp(os.tmpdir())` with a
  `settings.yaml` pointing at the e2e SSE server (copy the shape of `~/.kumo/settings.yaml` written by kumo's setup).
- Pipe pty output into `@xterm/headless`. Helpers: `screen(): string[]` (visible lines), `waitFor(text, ms)`,
  `waitStable(ms)`, `press(key)`.
- Own server `test/e2e/sse-server.ts`: OpenAI `/v1/chat/completions` streaming + `/v1/models`. Scripted per test:
  `reasoning_content` deltas, text deltas, `tool_calls` deltas, per-chunk delay, records every request body.

## Scenarios (one test each; save `screen()` to `__screens__/<name>.txt` at the key moment)
1. **Reasoning:** 40 reasoning lines mixing `\n`, `\n\n`, emoji, CJK, one 300-char line. At every snapshot (every 50 ms)
   at most ONE visible line contains `💭`. At the end: `thought for` is shown.
2. **Escape:** 200 text chunks, 100 ms apart. Escape after 1 s → screen stable within 1 s, server sees the connection
   closed, the editor accepts a new prompt and a second turn works.
3. **Tool call end to end:** the server answers a `tool_calls` for `read` of `note.txt` in the project → `● read` then
   `✓ read`, and the 2nd request contains the tool result. Qwen's fake got `EMPTY_RESPONSE` here. BOS verified the same
   flow WORKS against real llama.cpp, so the difference is in the fake's SSE format: find it, and write the cause in the
   report (compare with llama.cpp's real stream: `"finish_reason":"tool_calls"`, `index`, `id`, arguments chunking).
4. **Modes:** Tab shows Plan, Tab again Build. Shift+Tab: Ask → Auto → Full access asks confirmation, then the red badge.
5. **Keys:** ctrl+c clears a typed prompt; ctrl+d exits with code 0 in < 5 s.
6. **Resize:** `pty.resize(60, 20)` during reasoning → still one `💭` line, no line longer than 60 cells.
7. **Approval:** Ask mode, the model calls `write` → select shows Allow once / Always / Reject; Down, Down, Enter →
   the file is NOT created.

## CI

Per scenario: pass/fail + the screen dump. List of kumo bugs found (with dumps). Cause of the EMPTY_RESPONSE.
