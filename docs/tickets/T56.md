# T56 — Mouse selection: drag, release, copied, with a top-right notice

## The problem
Selecting a command, a path or an error line in kumo means dragging with the mouse and then pressing
ctrl+shift+c. The drag already works: kumo renders on the main screen and never enables mouse
reporting, so the terminal emulator owns the selection. What is missing is the second half, the part
every other agent CLI has: **releasing the button copies, and kumo says so.**

`ARCHITECTURE.md` parked this on `later | mouse/keyboard control, OFF by default`. The "OFF by
default" half is about *click to act* (clicking a tool to expand it, clicking a path to run it).
Selecting text and copying it is not control, it is reading, so it lands now.

## 0. The trade this ticket makes, stated once
To see the drag, kumo must turn mouse reporting on (`?1000 ?1002 ?1006`). While it is on, **the
terminal's own drag-selection is suspended inside kumo's area**, so kumo also has to paint the
selection itself. Konsole's context menu on right-click is likewise gone for that area. This is the
same trade pi-tui makes on its alt screen; the difference is that kumo keeps the main screen and its
native scrollback, which is not negotiable (T55).

**And the wheel.** kumo has no scrolling of its own (`chat-layout.ts`: "the scrollback belongs to the
terminal"), so the wheel is the only way to read back through a long transcript. Once reporting is
on, the wheel arrives as a button report and the transcript stops scrolling. There is no terminal
mode for "buttons but not the wheel", and forwarding the wheel by moving the cursor would desync
`TuiMainScreen`, which tracks the hardware cursor itself. So:

- a **form** outranks the preference: while a question or a permission prompt is up, the mouse goes
  back to the terminal, because that is exactly when the user reads what came before to answer it;
- outside a form the user chooses, with `/mouse` or `KUMO_MOUSE_SELECT=0`, and the notice says what
  the choice costs.

`?1003` (all-motion) stays off: a selection does not need 60 events a second, and the wheel is not
bound to anything.

## 1. Selection
- press sets the anchor, drag moves the focus, release ends the gesture.
- A press and a release on the same cell is a click, not a selection: nothing is copied and no
  notice appears. Every terminal behaves this way, and a notice that fires on every click is a
  notice nobody reads.
- The selection is painted in reverse video while it is alive, and the paint re-emits reverse video
  after every SGR code so that a nested colour reset inside the selected run cannot cancel it.
- Right and middle buttons are the terminal's. Wheel events are parsed and dropped.
- Both encodings are parsed: SGR (`?1006`, what Konsole, kitty, foot and xterm send) and X10
  (the 6-byte legacy form), so a terminal that ignores 1006 still selects.

## 2. Copy
Release copies through the first writer that is actually installed, text on **stdin** (never argv,
a selection can be a megabyte of scrollback):
- Wayland: `wl-copy`. X11: `xclip -selection clipboard`, then `xsel`. macOS: `pbcopy`. Windows: `clip`.
- No writer installed: OSC 52 (`\x1b]52;c;<base64>`), and only then. A bare OSC 52 can print
  "copied" and leave the clipboard untouched, so it is the last resort, never the first, and the
  notice says which path ran.
- The writers daemonize (that is how they own the selection), so a writer that has not exited after
  1.5 s counts as working. A spawn failure is a failure and is reported as one.
- Both directions now exist: T29 reads images out of the clipboard, T56 writes text into it.

## 3. The notice
One overlay, anchored `top-right`, `nonCapturing` so it never steals a keystroke from the editor,
`margin: 1`. Showing a second one replaces the first. It expires on its own (2.5 s) and is dropped
early when the user starts typing. Text is the only thing it carries: `Copied 42 chars` or the
reason it failed.

The 3 s notice line above the editor stays for mode changes and errors. This is a different job:
a confirmation of something that happened, in the corner, gone in seconds.

## Out of scope, on purpose
- Double-click word selection and its path/kebab-case exceptions (pi-tui's `alt-screen-search`).
- Copy on wheel, copy on click without a drag, a "copy last reply" command.
- Anything that *acts* on a click. Mouse as control stays off.

## Acceptance
- A mouse sequence never reaches the editor as text (today it is typed into it).
- Click without movement: no copy, no notice.
- Drag across lines: the copied text is the visible text, ANSI stripped, right line range, mapped
  through the viewport offset (the frame is taller than the screen on the main screen).
- The reverse-video paint touches the selected cells only, and survives an SGR reset inside them.
- Release copies exactly once per gesture, whatever the number of drag events.
- Writers per platform; OSC 52 only when no writer is installed.
- A report split across two reads is one gesture: pi-tui hands the listeners the raw chunk with no
  reassembly, and a press lost to a split takes the whole drag with it.
- A report is ignored while the app has not asked for the mouse.
- `KUMO_MOUSE_SELECT=0` and `/mouse` both give the wheel back, and a form does it by itself.
- The notice is anchored top-right, does not take focus, expires, and is replaced by the next one.
- The e2e keyboard suite is unchanged: enabling mouse reporting must not cost a keystroke.
