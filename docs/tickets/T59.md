# T59 — What the turn did to the files

## The problem
A tool call says what it was asked to do (`write src/ui/mouse.ts`) and the T55
receipt says how long the turn took. Neither says what is now different on disk,
which is the only question that matters after a command ran: a `bash` line ending
in a quiet `ok` could have touched eleven files, and nothing in the transcript
would ever admit it. The paths that do appear are per tool call, hidden behind
`ctrl+o`, and mixed in with every `read`.

## What it does
The turn is measured against the workspace, not against the tool names.
`git status --porcelain=v1 -z` is read when the turn starts and when it ends, and
the difference is printed under the receipt:

```
✓ 4 tools · 41s · 1.2k tokens
  changed  src/ui/changes.ts  src/ui/mouse.ts  +2 more
```

- **Ground truth, not a guess.** A `sed -i` inside a command counts exactly like
  a `write` tool, because it is the same measurement.
- **Attributed to the turn.** A file the user edited in their own editor during
  those forty seconds is in both readings, so it is not in the delta. Without the
  opening reading the line would claim the user's own work.
- **Two process spawns per turn**, both fire-and-forget: the opening one is not
  awaited, because a slow repository must never delay the first token, and the
  closing one lands after the receipt, which is synchronous on purpose.
- **`-z`, not the default porcelain.** A path with a space arrives as
  `?? "a file with spaces.txt"` without it, and one with a quote or a backslash
  arrives escaped. A rename carries its source in the next field, which is
  dropped: the destination is the path that exists now.

## The fallback, and its smaller claim
Outside a git repository there is nothing to measure, and the fallback is what the
tools declared: `write`, `edit`, `multi_edit`, `notebook_edit` and their `file_path`.
That is a strictly smaller claim, and the two sources are never mixed: git answers
or it does not.

A `read` names a path too, and is deliberately **not** counted: the workspace can
contradict it, and a line that lies is worse than no line.

## Out of scope, on purpose
- **A diff.** The lines added and removed per file are a rendering component of
  their own (colour per line, navigation, folding) and a ticket of their own.
- **Untracked-ignored files.** `.gitignore` decides what a workspace is, so an
  ignored file is invisible here. That is a real limitation, stated rather than
  worked around: the alternative is walking the tree, which is slow and racy.
- **A cumulative "session changes" view.** This is per turn, because a turn is
  the unit the receipt already uses.
- Renames as renames: the destination is listed, the source is not, and neither
  is labelled. A rename label would need the source path kept for a line nobody
  asked for.

## Acceptance
- Porcelain is read with `-z` semantics: a path with spaces is a path, and a
  rename contributes the file that exists.
- The delta between two readings names only what moved, including a file the turn
  deleted, and nothing at all when the two readings agree.
- A file changed by hand during the turn is in both readings and is not reported.
- Outside a repository the declared tool paths are used, deduplicated, and the
  tools are not consulted when git answered.
- A `read` is never counted as a change, and half-streamed arguments are not a path.
- The line prints at most three paths and a `+N more`, collapses to a count when
  the terminal is too narrow, and prints nothing for an empty list.
